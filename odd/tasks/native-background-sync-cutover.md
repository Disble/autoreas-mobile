# Native background sync cutover

## Objective and authority
Complete the Kotlin background-sync migration on `test/sync-core-assurance` (starting at `a13381f`) without losing delivery when the native foreground service is absent. The maintainer authorized code changes and later use of the connected Android tablet and Docker on 2026-09-25, asked for code work before device validation, and requested a final migration report. Do not push, open a PR, release, or commit without fresh explicit confirmation after validation and diff review.

ADR 008 chooses Kotlin as owner of the background cycle. Its JS/Kotlin duality is temporary; foreground TypeScript domain apply is intentionally retained. This follow-up re-scopes deferred T8 in `odd/tasks/mobile-sync-native-engine.md` rather than rewriting that historical record. T8's proposed removal of the *native ticker* is obsolete: it is now the native foreground service's only tick source and must remain.

## Current evidence / unresolved risks
- Closeout update (2026-09-26): M3 has replaced the Expo/JS background task with a native WorkManager floor. The bullets immediately below record the *pre-cutover* design baseline; see the dated M4 evidence and closeout at the end for the current state. M4 remains partial and M5 awaits explicit delivery approval.
- `src/features/sync/use-sync-runtime.ts` registers both native FGS and an Expo WorkManager floor. `background-sync.task.ts` still enters a JS callback; `background-sync.helpers.ts` calls Kotlin first and falls back to `runJsBackgroundSyncCycle()` if the native module is absent or returns `unavailable`. It no-ops while the native ticker owns the background.
- `SyncForegroundService.kt` runs `SyncEngineRunner` directly, without JS. The foreground UI uses TypeScript for domain apply and is not a removal target.
- The initial six fixture-recorded JS/Kotlin wire divergences were already present in the native engine before this cutover. One native data-shape gap (`genres[]` with a non-string member) is now guarded before staging; five strictness/coercion policy differences remain and are not a fallback-retirement gate. Independent verification also noted two pre-existing, unrecorded strictness differences (`changed_fields[]` member dropping and whole-value `genres: null`); neither was introduced here or silently reclassified as fixed.
- The old T8 acceptance depended on trigger reliability and 24-hour/device metrics that were not established. An existing installed device may have an Expo-scheduled job; its upgrade transition must be handled explicitly.
- Read-only mapping selected a native WorkManager periodic floor in `modules/sync-engine`, not the existing FGS alarm alone: when FGS is off, the floor must still invoke the Kotlin engine with the presence gate, native status projection, lease and watchdog. The native ticker remains. An old Expo-scheduled job must be cancelled during upgrade, not merely orphaned.
- This preserves the shipped FGS behavior while replacing the JS background callback with a native Worker. Foreground JS may request the native registration at app initialization; once registered, WorkManager owns wakeups without JS. The previously excluded case of a fresh install that never finishes initial startup is not silently claimed covered.

## Scope / non-goals
Deliver a native-only background cycle **and** a native background trigger/floor when FGS is off, with a safe upgrade transition from the old Expo job. Preserve the native foreground-service tick, its lease/watchdog/status behavior, battery/absence policy, durable diagnostics, and the foreground TypeScript domain apply. Do not rewrite product UI, bridge schemas, or unrelated diagnostics and quality debt. No change to reboot-before-first-launch expectations unless explicitly authorized; an earlier maintainer decision excludes it. Do not modify dependencies by hand.
