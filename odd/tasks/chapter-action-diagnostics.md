# Chapter action diagnostics

## Objective and problem
Make the four chapter-control callbacks (`capPlus`, `capMinus`, `capPlusHalf`, `capMinusHalf`) diagnosable with a few question-driven observations delivered through **only** `POST /api/sync/diagnostics`. Today mutation errors enter a volatile JS ring, foreground sync does not capture it, JS can duplicate cycle telemetry between diagnostics and reconcile, and native FGS does not flush the diagnostics outbox. A JS callback is not proof of a physical tap; disabled buttons and a non-running JS thread cannot be observed at this boundary.

## Scope and constraints
- Branch/worktree: `feat/chapter-action-diagnostics` at `../autoreas-mobile-chapter-telemetry`, isolated from the dirty `test/sync-core-assurance` worktree.
- Capture only events answering: did an enabled-button JS callback run; was it dropped/no-op; did the local write commit/fail; did the immediate post-write sync succeed/fail. Keep a bounded, allowlisted action/outcome vocabulary and correlation sufficient to distinguish a callback from its outcome. Do not send anime IDs, titles, patches, SQL, exception messages or arbitrary strings.
- Persist each observation AT EVENT TIME into the existing durable diagnostics outbox (`createSyncDiagnosticsOutboxStore().enqueue`), whose own connection to `autoreas-telemetry.db` is deliberately outside `withLocalWrite`; do not route chapter observations through the volatile in-memory ring nor wait for a later headless cycle.
- Keep one compact, extensible event vocabulary (one `chapter_action` event with a closed `phase` plus optional closed `outcome`/`reason`/`duration_ms`/`correlation_id`), so future diagnostics add vocabulary values only. Kotlin transports stored JSON opaquely via the existing HTTP transport and must not learn new event vocabulary. Remove duplicate `client_telemetry` from JS/native reconcile requests. Preserve pending operation reconciliation and keep diagnostics best-effort.
- Do not include anime identity in the payload. Two sequential actions must remain distinguishable; unique outbox ids per observation, correlation id shared across one action's observations.
- Bridge acceptance of the additive envelope is not verifiable from local mobile code; confirm before relying on it.
- Avoid edits to historical OpenSpec/docs artifacts and the other session's work. Do not commit without explicit user confirmation after validation and diff review.
- Known limitation: no native physical-touch tracing; no JS event exists if JS callback does not execute.

## Acceptance
- Bridge receives chapter observations only through `/api/sync/diagnostics`, with a durable path after callback receipt and no anime-specific payload; foreground JS or native FGS can flush pending envelopes without altering sync success/failure.
- The four questions are individually answerable or explicitly reported as unobservable; two sequential actions must not accidentally coalesce across distinct outcomes. No button telemetry is included in `/api/sync/reconcile`, and native reconcile no longer carries minimal `client_telemetry`.
- Delivery failures leave eligible envelopes pending according to existing bounded retry policy; no new telemetry failure blocks a user mutation or a normal sync cycle.
