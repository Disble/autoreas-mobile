# ODD — Mobile database ownership and self-service recovery

**Status:** T1 in progress; no implementation yet. Branch: `perf/release-cache-upload-pruning`. Commits, push, release, tablet data changes, and EAS credential access are explicitly not authorized. Existing untracked `docs/mobile-sync-engine-workflow.md` and `odd/tasks/mobile-sync-engine-workflow-map.md` must be preserved.

## Objective and evidence

Prevent two independently linked SQLite engines in one Android process from writing `autoreas.db`, and let a normal user recover from **confirmed physical corruption** without a fatal startup loop or technical support. The v1.7.0 tablet's malformed main DB, `user_version=16`, intact required schema and empty current WAL are observed; its specific damage event is unknown. Corrected offline Linux scratch tests show successful INSERT+COMMIT followed by missing rows in mixed-instance WAL runs, even though integrity checks pass; same-library and separate-process controls do not lose rows. This validates a structural hazard, **not** the cause of the tablet's structural corruption. Audited evidence: `C:/Users/User/AppData/Local/Temp/autoreas-diag/dual-sqlite-lab/audit/evidence/AUDIT_REPORT.md` (frozen harness only). Current runtime authority is source, not historical plans.

## Scope, product constraints and seams

- Preserve existing fast healthy-start path: no extra integrity probe, Bridge round trip, or wait. Record a comparable healthy-path baseline and after-result; lack of authorized device build means on-device timing may remain pending.
- Distinguish transient `SQLITE_BUSY`/`SQLITE_LOCKED`, logical missing schema, confirmed physical damage, incompatible version and unknown errors. Only confirmed damage offers reset. Existing bounded retries and startup deadline remain authoritative.
- Public behavior seams: `prepareForegroundDatabase`/startup diagnostic and `StartupBoundary` for safe failure decisions; native background runner and status projection for ownership/readiness; one reset boundary covering native jobs, Expo provider lifetime, DB/WAL/SHM deletion, durable restart state; setup/pairing/snapshot gate before catalog. Tests live under `tests/` (or native `src/test`) and use disposable synthetic databases. RED → GREEN → MUTATE → REFACTOR for changed helpers/hooks. Assert rejection paths, double-press and crash-resume.
- A reset requires one explicit user confirmation warning that unsent Mobile changes may be lost. Never assert Bridge has them. Close all owners and exclude JS, WorkManager and FGS during reset; use a SQLite/Android deletion API only after closure, never manually remove an open WAL. Reset only `autoreas.db` and sidecars, not all app settings or telemetry. Recovery completes only after normal setup, pairing and successful snapshot persistence; Bridge offline remains in setup. If integrated reset fails, explain and offer Android app-storage settings as a last resort, warning that **clear storage** deletes all app data/settings (not clear cache).
- Verify the installed framework's default corruption handler behavior before depending on its policy; do not use the tablet or build another lab APK without separate authorization. Sensitive connection values, SQL and user data must not enter diagnostics. Update `docs/mobile-sync-engine-workflow.md` for every changed engine edge; split the 496-line map into readable documents rather than exceeding 500 lines.
- Work-unit branches remain uncommitted by explicit user instruction; each task records test/runtime evidence, rollback boundary and pending checks instead of inventing commit identities. Keep writers single-threaded and review slices cohesive (~400 authored lines threshold).

## Chosen ownership strategy (T1 decision)

**Decision: isolate the native Kotlin SQLite owner into a dedicated `:sync` Android process; do not attempt to share one SQLite core.**

Evidence behind the choice, all from this repository or official documentation:

- A single shared core is not achievable locally. Expo's Android SQLite is `internal class NativeDatabaseBinding` in `node_modules/expo-sqlite/android/src/main/java/expo/modules/sqlite/NativeDatabaseBinding.kt` with `System.loadLibrary("expo-sqlite")`; `internal` is Gradle-module-scoped so `:sync-engine` cannot reference it, `sqlite3.c` is compiled straight into `libexpo-sqlite.so` (`node_modules/expo-sqlite/android/CMakeLists.txt`), and `node_modules/expo-sqlite/android/build.gradle` exports no `prefab` block. Reaching it would need `dlopen`/`dlsym` against a private symbol set, or recompiling `sqlite3.c`, which recreates a second core and therefore the original hazard. The only stable route to one core is upstreaming a public Android API into expo-sqlite, which is outside this repository's authority.
- Process isolation is achievable with documented, public APIs. AndroidX `RemoteCoroutineWorker` (`androidx.work:work-multiprocess`) runs `doRemoteWork()` in the process hosting a bound `RemoteWorkerService`, so the periodic floor can leave the main process without replacing WorkManager. The first scout's claim that WorkManager must be replaced was wrong.
- The dependency is fetchable here: `https://dl.google.com/dl/android/maven2/androidx/work/work-multiprocess/2.11.1/work-multiprocess-2.11.1.pom` answered HTTP 200 (Maven Central answered 404), and the local Gradle cache does not contain the artifact yet. JDK 21 and `ANDROID_HOME` are present and `android/` is generated, so Kotlin unit tests can run.
- Which writers must move, from source: the foreground service (`SyncForegroundService`, currently no `android:process`) and the WorkManager floor (`SyncFloorWorker`, a `CoroutineWorker` today). `SyncEngineRunner` is a Kotlin `object` (per-process singleton) and the status projection opens its own framework connection. The JS-called `runOnce` entry point exists in `SyncEngineModule` but has no caller in `src/`, so the live main-process DB writers are those two.
- Moving them is not sufficient by itself. `SyncFloorWorker`'s gate `SyncTickerOwnership.ownsBackground` read `SharedPreferences` with `Context.MODE_PRIVATE` while `persistTickingState` writes with `apply()`, so a worker in `:sync` would read a stale flag and could skip every tick after the user stops the ticker. Slice A replaces that answer with the armed alarm's own `PendingIntent` token, which is system-level state and therefore consistent across processes.

Known costs and obligations that stay explicit rather than hidden:

- `MainApplication` calls `loadReactNative(this)` with no process guard, so a `:sync` process would boot React Native/SoLoader unless that is guarded.
- `RemoteWorkerService` and `SyncForegroundService` need `android:process=":sync"`, and `SyncFloorScheduler` must pass `ARGUMENT_PACKAGE_NAME`/`ARGUMENT_CLASS_NAME` in the work request.
- `SyncEngineRunner`'s process-wide singleton and its watchdog become one instance per process; only the `sync_cycle_lock` lease plus `BEGIN IMMEDIATE` still serializes attempts across processes.
- The Robolectric harness drove `SyncFloorWorker` through `TestListenableWorkerBuilder`, which cannot construct a remote worker (verified: `RemoteListenableWorker.startWork()` is `final`), so the behavior was extracted into `SyncFloorAttempt` first — done in slice B1.
- Both `:sync` components exist only in the generated manifest, produced by prebuild from the config plugin: a hand-edit under `android/` would be lost on the next prebuild, and `android/` is excluded from git. Review `plugins/withAndroidForegroundSync.js`, not the generated tree.
- Real-Android obligations still unverified: that WorkManager binds `RemoteWorkerService` in `:sync` so the floor opens the database there; that a `:sync` tick does not boot React Native on every supported API level; that the main process now opens no framework connection to `autoreas.db`; and the documented multiprocess caveat that WorkManager's own initializer still runs in `:sync` (a separate database file, so outside this hazard, but worth confirming).
- This slice cannot be proven on hardware from here: Robolectric is a single-process JVM, and a real lab build contacts Expo for EAS signing credentials, which needs its own explicit authorization. The needed device evidence is specific: install an authorized lab APK over the existing install, arm the ticker, kill the app process, then read ownership from the `:sync` process (`adb shell dumpsys alarm` plus the floor status); repeat after `stop()` to prove both the token and the alarm are gone; then cover reboot, force-stop and app-update. No `android:process` declaration exists anywhere in the tree yet, so even a device run cannot exercise a two-process split until slice B lands.
