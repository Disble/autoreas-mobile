- Technical artifact language follows current repository docs (English); conversation remains Spanish.
- No source edits, device operations, data restoration, APK build, publication, or implicit commit.
- Route: delegated read-only mapping (4+ relevant files); one bounded documentation writer only if multiple non-trivial files require editing. Parent owns final verification.
- Delivery forecast: one new documentation file, roughly 250–400 authored lines plus this progress file; if the map naturally exceeds that, readability controls the split, not an artificial limit.
- TDD mode: not applicable to documentation-only work; functional verification is source traceability plus Mermaid syntax/render and repository documentation checks where available.
- Delivery strategy: ask-on-risk if authored changes exceed about 400 lines; no push/PR/merge without user decision. Commit pending explicit user request.

1. **R1 — Reproduce on Android without user data.** **Not implemented.** Still pending an authorized device run: run the actual Expo and framework SQLite implementations against one disposable WAL database, with same-library and separate-process controls, count `INSERT DONE` + `changes()==1` + `COMMIT OK` against persisted unique rows, and capture lock outcomes and each connection's SQLite version, VFS and journal mode. Stop if the app database path is touched.
2. **R2 — Make `autoreas.db` a single-core-per-process boundary.** **Implemented, by a different route than proposed — [Implemented].** Sharing one SQLite implementation is not achievable locally (Expo's `NativeDatabaseBinding` is `internal`/Gradle-module-scoped, `sqlite3.c` is compiled into `libexpo-sqlite.so`, and no `prefab` block is exported), so the native owner was isolated instead: `plugins/withAndroidForegroundSync.js` declares `SyncForegroundService` and `androidx.work.multiprocess.RemoteWorkerService` with `android:process=":sync"` and guards `MainApplication.onCreate`; `modules/sync-engine/android/src/main/java/expo/modules/syncengine/SyncEngineProcess.kt` fails closed for the JS-callable `runOnce`; `SyncFloorWorker.kt` extends `RemoteCoroutineWorker`; `SyncFloorScheduler.kt` stamps the request with the remote service identity. **Pending:** the Android stress acceptance (retain every confirmed insert, prove the main process opens no framework connection) and the `FULL`/`IOERR` assertions, which need a device.
3. **R3 — Exclude background writers from the schema window.** **Implemented — [Implemented].** `SyncEngineDatabases.kt` owns the Kotlin twin `EXPECTED_SCHEMA_READINESS_VERSION` (16), `resolveAppDatabaseReadiness`, the read-only `user_version` reader and `probeAppDatabaseReadiness`; `SyncEngineRunner.kt` refuses before arming its watchdog or queueing; `SyncEngineRuntimeStatus.kt` refuses before opening a connection; `tests/infrastructure/db/native-schema-readiness-twin.test.ts` guards the twin against the migration journal length. **Pending:** forced-tick device evidence and the versions/connection/lock stage logs.
4. **R4 — Contain physical corruption without a fatal loop.** **Implemented at the domain level; one sub-item deliberately not implemented — [Implemented] unless noted.** `src/infrastructure/db/startup/startup.errors.ts` adds `SchemaIntegrityError`; `src/infrastructure/db/startup/startup.helpers.ts` throws it for a failed `PRAGMA quick_check` and rethrows anything that is not `SchemaValidationError` before migrations; `src/features/startup/startup.helpers.ts` classifies it `corruption`; `src/infrastructure/db/recovery/` authorizes corruption-only resets and orders durable intent → stop native writers → awaited close → delete → prepare → clear intent; `src/features/startup/recovery/` plus `src/features/startup/ui/StartupBoundary/StartupDatabaseResetDialog.tsx` present it; `SyncEngineDatabases.deleteAppDatabaseAndSidecars` deletes through framework `SQLiteDatabase.deleteDatabase(File)`. **Not implemented:** replacing the native default corruption handler so forensic files are not silently deleted (AOSP's default handler may delete DB files and the installed framework's behavior is unverified). **Pending:** the injected-damage restart reaching setup, and `busy`/`FULL`/`IOERR` never auto-resetting a healthy database, both on a device.
